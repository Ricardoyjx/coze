## 项目名称：招聘JD自动生成与简历初筛Agent

### 1. 项目背景介绍

**行业痛点**：  
我公司（某中型互联网科技企业，员工300+，年招聘量约150人）HR部门每月需处理20+个岗位的招聘。传统流程中，HR需手动撰写岗位说明书（JD），每人耗时1~2小时，且不同HR风格差异大，关键要求易遗漏。简历初筛阶段，一个普通运营岗能收到200+份简历，HR逐份阅读平均耗时3分钟/份，整体初筛耗时超10小时/岗，且存在主观偏差。

**技术机遇**：  
大语言模型（LLM）具备文本理解与生成能力，结合RAG与工作流编排，可自动化完成JD生成与简历评分。我们决定开发**招聘JD自动生成与简历初筛Agent**，将HR从重复劳动中释放，提升招聘专业度与效率。

**项目目标**：  
构建一个Agent系统，HR输入岗位名称和关键要求（如“高级Java开发工程师，5年经验，熟悉微服务”），系统自动输出：

- 一份结构完整、符合公司规范的JD（含职责、任职资格、加分项）
- 对上传的一批简历（PDF/Word）进行解析、打分、排序，输出推荐列表

系统采用**1个父Agent + 2个子Agent**架构，确保职责分离、可扩展。

### 2. 项目业务介绍

- **父Agent（调度器）**：接收HR输入，理解意图，协调子Agent工作流。当HR上传简历包时，父Agent触发简历初筛流程；当HR要求生成JD时，触发JD生成流程。父Agent还负责记录会话上下文、调用外部知识库（公司JD模板库、岗位能力词典）。
- **子Agent A – JD生成Agent**：根据HR提供的岗位名称、关键词、团队风格等，结合公司内部JD模板（向量库），生成符合要求的JD文本。支持迭代修改（HR可反馈“职责太宽泛”等，Agent重新生成）。
- **子Agent B – 简历初筛Agent**：接收JD文本（可由子Agent A生成或HR直接提供）和一批简历文件，进行：
  - 简历解析（提取姓名、联系方式、工作经历、技能、教育背景）
  - 与JD要求的匹配度计算（基于关键词、语义相似度、年限匹配）
  - 输出评分（0-100分）及排序列表，标注高亮匹配点与缺失项。

**业务流程**：  
HR登录前端页面 → 输入岗位需求 → [父Agent] 调用子Agent A生成JD → HR确认/修改 → 发布JD → 收取简历 → 上传简历包 → [父Agent] 调用子Agent B初筛 → 展示评分排序结果 → HR最终筛选。

### 4. Coze或者Dify工作流编排

我们选用**Dify**（开源、支持工作流编排、企业级扩展）。工作流设计如下：

**父Agent主工作流（Workflow）**：

```
[Start] → [意图识别节点(LLM)] 
    → 分支1(生成JD) → 调用子Agent A子流程 → 输出JD → [End]
    → 分支2(初筛简历) → 调用子Agent B子流程 → 输出评分报告 → [End]
```

**子Agent A – JD生成工作流**：

```
[输入: 岗位关键词] → [检索知识库: 相似岗位JD模板] → [Prompt组装节点] 
→ [LLM生成JD] → [输出格式校验] → [人工反馈循环(可选)] → [保存至数据库] → [返回JD文本]
```

**子Agent B – 简历初筛工作流**：

```
[输入: JD文本 + 简历文件列表] → [循环节点: 遍历每个简历]
    → [文件解析节点(pdf/word)] → [LLM信息提取节点] 
    → [评分计算节点(代码节点)] → [存储评分结果] → [累加]
→ [排序节点(按评分降序)] → [生成可视化表格] → [返回结果]
```

在Dify中，各节点通过变量传递，LLM节点采用高性价比模型（如GPT-4o-mini），评分计算使用Python代码节点确保确定性。

### 5. Prompt工程设计

我们设计了两组核心Prompt，经多次迭代优化。

**1. JD生成Prompt（用于子Agent A）**：

```
# 角色
你是一名资深HR专家，擅长撰写清晰、专业、符合劳动法规的岗位说明书。

# 任务
根据以下信息，生成一份完整的招聘JD，包含：岗位名称、岗位职责(4-6条)、任职资格(硬性条件)、加分项(可选)。

# 输入信息
{关键词描述}

# 公司风格
我们是一家快速发展的互联网科技公司，强调结果导向和团队协作。JD应避免性别、年龄等歧视性词汇，突出技术挑战和成长空间。

# 参考模板（检索到的相似JD）
{最相似JD模板}

# 输出格式
严格按以下Markdown结构输出：
## 岗位名称：xxx
### 岗位职责
- ...
### 任职资格
- ...
### 加分项
- ...
```

**2. 简历解析与评分Prompt（用于子Agent B中的LLM提取节点）**：

```
# 角色
你是一名严谨的招聘助理，负责从简历文本中提取结构化信息。

# 任务
从以下简历内容中提取字段，并按要求输出JSON。

简历内容：
{resume_text}

请提取：
- name (姓名)
- phone (手机号)
- email (邮箱)
- total_work_years (总工作年限，数字)
- skills (技能列表，如["Python","项目管理"])
- education (最高学历，如"本科")
- last_company (最近一家公司名称)

如果某项信息无法确定，填写null。

# 评分逻辑（在代码节点实现，而非LLM，以保证稳定）
```

> 注：评分计算移入代码节点，避免LLM输出不稳定分数。

### 6. 项目前端页面

采用**React + Ant Design**构建，适配桌面端。主要包含三个页面：

- **页面1：JD工作台**  
  - 左侧表单：岗位名称、关键词输入框、附加要求（多行文本）  
  - 右侧展示区：生成的JD（实时预览），支持“编辑”和“重新生成”按钮  
  - 底部按钮：“保存JD”、“进入初筛”

- **页面2：简历初筛面板**  
  - 上方显示当前JD摘要  
  - 中间为拖拽上传区（支持批量上传PDF/Word）  
  - 下方为结果列表：表格展示候选人姓名、评分、匹配摘要（绿色高亮匹配项，红色标记缺失项），可点击查看详细比对报告  
  - 图表：评分分布柱状图、技能匹配词云

- **页面3：历史记录**  
  - 展示所有生成的JD及对应的初筛任务，支持搜索和重新导出。

**前端亮点**：采用流式输出（SSE）展示JD生成过程；简历上传显示解析进度条；评分结果支持一键导出Excel。

### 7. 项目落地效果

在为期2周的试点中，我们选取真实历史数据：3个技术岗（Java、前端、运维）和2个非技术岗（运营、销售），共收集简历450份。

**量化成果**：

- JD生成时间：从平均**90分钟**降至**2分钟**（含HR确认修改），生成JD与HR最终录用版本的相似度（BLEU）达0.82。
- 简历初筛时间：从平均**10小时/岗**降至**15分钟**（含上传、解析、评分），HR对Top5推荐的采纳率为**86%**（即最终面试的候选人中有86%出现在Agent推荐的前5名）。
- 漏筛率（合格但评分低至30分以下）仅**3%**，优于纯关键词筛选的12%。

**用户反馈**：  
HR团队表示“基本无需人工书写JD，只需微调”，“简历评分维度比人工更一致，避免了疲劳导致的漏看”。

### 8. 项目问题和解决方案

| 问题                                                         | 解决方案                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| **1. 简历解析错误**：部分PDF含图片或复杂表格，提取不到文字。 | 引入OCR后备方案（EasyOCR），先尝试pdfplumber，失败则调用OCR。 |
| **2. JD生成过于泛化**：缺少行业特定术语（如金融行业需“合规经验”）。 | 在知识库中按行业细分JD模板，并在Prompt中加入“若岗位关键词包含金融/医疗等，强化对应领域要求”。 |
| **3. 评分偏袒简历长度**：长简历得分虚高。                    | 评分时归一化处理：技能匹配按比例计算，且添加“冗长惩罚项”（超过2页扣2分）。 |
| **4. 并发上传导致后端超时**。                                | 改为异步任务队列（Celery + Redis），前端显示处理状态，完成后消息通知。 |
| **5. LLM调用成本高**：批量简历解析调用次数过多。             | 对明显不匹配的简历（如学历不符）先经过规则引擎快速过滤，仅对候选集调用LLM解析，减少30%调用量。 |

### 9. 项目价值和未来展望

**当前价值**：

- **效率提升**：综合节省HR招聘时间约70%，加速招聘周期（从发布到初筛完成由5天缩至1天）。
- **质量一致**：JD标准化，避免遗漏关键要求；简历评分客观可追溯，降低招聘中的偏见。
- **数据沉淀**：所有JD及匹配记录纳入公司人才知识库，可分析岗位需求趋势。

**未来展望**：

- **多模态扩展**：支持解析视频简历（通过语音转文字+情感分析）和作品集图片。
- **主动寻源**：结合公开简历库（如GitHub、领英），Agent自动生成候选人短名单并发送邀请。
- **面试辅助**：根据简历和JD，自动生成个性化面试题，并模拟面试官进行初轮问答。
- **多租户SaaS化**：包装为产品，对外提供中小企业招聘Agent服务。

### 10. 项目感悟和分享

作为项目管理者，我深刻体会到：

1. **AI Agent不是魔法，而是工程化组合**：成功依赖于清晰的工作流设计、高质量Prompt、健壮的异常处理以及合理的成本控制。父Agent+子Agent的架构极大降低了模块耦合度，使前后端能并行开发。
2. **HR业务专家的深度参与是关键**：最初我们设计的评分维度偏重技术词频，但HR指出“稳定性”“团队协作”等软性指标也很重要。后来我们加入“最近工作时长”“项目角色描述”等字段，准确率才显著提升。
3. **小团队也能做“大模型应用”**：10人团队中仅1名算法工程师，但借助Dify低代码编排和成熟LLM API，2周即交付MVP。重点应放在数据清洗、用户体验和反馈闭环上。
4. **坑与收获**：最头疼的是简历格式“万国造”，我们花费约30%时间处理文档解析。建议后续项目优先采用统一格式（如仅支持PDF），或提前购买商业解析API。
5. **团队成长**：前后端同学通过本次项目都学会了写Prompt工程，测试工程师也转型为“AI测试”，设计对抗性输入（如伪造简历）。大家都认识到：AI不会取代我们，但会用AI的人会。

最后，感谢评审方的打分框架，促使我们结构化地思考并落地一个完整、可评估的AI Agent项目。期待后续迭代！
